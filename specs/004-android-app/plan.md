# Implementation Plan: Epic Replay on Android

**Spec**: `specs/004-android-app/spec.md` (revision 3) · **After**: specs 002 and 003 are merged (they are) · **Estimate**: about 146 hours (section 6); the two spikes decide how much of it is real

## 1. Approach

1. **Answer the two unknowns first, on a device** (T401, T402): can the engine look at an image on a phone, and can Media3 do the video the PC does. Nothing that depends on the answers starts before them. Both need the owner's phone.
2. **Change the shared contracts and the PC before any Android code** (T403, T404): the `network` location, the `on_device` kind, the consent wording in `shared/`. Each lands with tests on the PC side, with no change to anything the PC sends or says.
3. **Build the model choice end to end** (M2), since it is what the owner asked this spec to start with: settings and keys, the cloud client, the engine, the downloads, consent. This is a usable, testable app without a pipeline: pick where the models run, download, ask one question of each model.
4. **Port the plain-code stages against the conformance cases** (M3), adding the missing conformance areas from the Python code first, one area at a time.
5. **Build the media pipeline on what the spikes found** (M4), then the screens (M5), then measure on the phone and review.

Each milestone ends in something the owner can run on a phone. Every task follows the working rules of the repository: one commit per task, no guessed library behaviour (rule 2), no paid call without the owner's yes and the expected cost (rule 3), only frames to the chosen vision profile (rule 4).

## 2. The folders

```
android/
  README.md
  settings.gradle.kts  build.gradle.kts  gradle/  gradlew       the Gradle build (T405)
  app/                  Jetpack Compose UI, navigation, settings, results      (M2, M5)
  core/                 pure Kotlin, no Android classes: the stage ports, guards, the
                        model contract and its cloud client, the Kotlin loop of the Commentator,
                        the conformance runner; unit-tested on the JVM            (M2, M3)
  engine/               the JNI bridge and the llama.cpp build (CMake), the on-device
                        backend, the downloads                                    (M2)
  media/                Media3 Transformer pipeline: visuals, mix, compose, export (M4)
  native/               CMakeLists.txt, the patch if any, build notes for libllama and libmtmd
shared/                 read by the build as source sets / assets, never copied
  models/               + the on_device profiles                                  (T403, T410)
  copy/consent.json     the consent wording and its versions                      (T404)
  conformance/          + the areas added in M3
```

`core/` has no Android dependency so the conformance cases run in milliseconds on the JVM, on CI and on the owner's machine, with no emulator. Only `app/`, `engine/` and `media/` need a device or an emulator for their tests.

## 4. The model choice (spec FR-001 to FR-018)

- **Profiles.** Two `on_device` files: `gemma-4-e2b-device` and `qwen3-5-4b-device`, with `files` (name, url, sha256, bytes, role), the context size and the memory and storage floors measured in T401. The URLs and checksums come from downloading the files (T410) and are cross-checked against the publisher's own listing, not taken from a model card or from the download alone; downloads are HTTPS from an allowlist of hosts.
- **Storage of the choice.** One small file in private storage: for each role the chosen profile id. The keys are separate: a Keystore AES key wraps them, only ciphertext on disk, `allowBackup` off (FR-008).
- **The backends behind one interface**: `ModelBackend { look(...); chat(...) }` in `core/`; `CloudBackend` (HTTPS, from the profile, with the caps and the recorder) and `OnDeviceBackend` (in `engine/`, serialised, with a memory check). The Kotlin tests use `FakeBackend` and recordings.
- **Engine.** llama.cpp and `libmtmd` cross-compiled as one static library as voice-reps does (flags in FR-012), with a JNI bridge written for `look()` and `chat()`. `examples/llama.android` in the llama.cpp repository is the reference for the text path; the image path is what T401 tries. If it fails the on-device choice is text-only and the plan says so before M2 is built.
- **Downloads.** `HttpURLConnection` or OkHttp with `Range` resume, a `.part` file, a SHA-256 check, a storage check, and a Wi-Fi hint; from voice-reps only the first-launch gate and the crash log are reused.
- **Consent.** The consent screen reads `shared/copy/consent.json`; the record names the location; a run whose consent was for `device` or `local` is stopped before a cloud call (as `consent.require` does on the PC).

## 7. Risks

| Risk | Sign | Response |
|---|---|---|
| libmtmd does not run on Android as built | T401 cannot get an answer from an image | On-device is text-only; the first-run screen says so; vision is cloud; raise it with the owner before M2 |
| Qwen3.5 does not load in llama.cpp, or is far too slow | T401 | Its profile is not shipped; Gemma stays the only on-device option |
| Memory: the phone kills the app while the model is loaded | T401, T409 | `min_free_ram_mb` from measurement, refused before loading, never a crash |
| Media3 lacks slow motion, overlays or ducking | T402 | Decide with the owner: a custom effect, MediaCodec and OpenGL, or a bundled FFmpeg |
| The Kotlin Commentator loop is worse than agent-core's | T419 on the cloud profile | Keep the PC's structured draft path as the Android default and the loop only if it measures better |
| A shared change breaks the PC | T403, T404 | The PC's full checks after each; no word of the cloud consent changes |
| The signal scan differs between OpenCV builds | T413 | The tolerance written in the case; the scan is advice to the Spotter, not a fact |
